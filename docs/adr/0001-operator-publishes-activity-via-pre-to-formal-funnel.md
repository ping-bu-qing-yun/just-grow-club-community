# 管理者发布活动走「预活动 → 正式发布」两步漏斗

需求要求只有管理者（小CC）能发布活动，且 PRD §10.5 把活动生命周期建模为「预活动 → 正式报名」。我们决定：管理者填完活动表单后，活动先进入「预活动」状态（对用户可见、不可报名），需管理者再点一次「正式发布」才转为「正式活动」并开放报名。本期**不**实现 PRD §10.3–10.4 的「AI 提案生成 / 小CC审核提案」漏斗——那是独立的运营功能，与「谁能发活动」的权限需求正交。

## Considered Options

- **直接发布**：填完即上线、可报名。改动最小，但与 PRD 的预/正式活动二态模型冲突，且抹掉了管理者「先预告、再开放报名」的运营节奏。
- **走完整 AI 漏斗**：AI 生成草案 → 小CC审核 → 预活动 → 正式发布。忠于 PRD 全貌，但把一个权限需求膨胀成运营后台，且依赖尚未接入的 AI 模型。

## Consequences

- `activities.lifecycle` 取值为 `pre | formal | archived`；`POST /api/v2/activities` 默认落 `pre`，`PATCH /api/v2/activities/:id/lifecycle` 仅允许 operator 执行合法前向转换。
- 普通用户在预活动阶段使用「预约兴趣」，写入 `activity_members.status='interested'`，不占正式名额、不创建群聊；转为 formal 后再次确认才升级为 `joined`。
- 发布成功反馈明确使用「预活动已创建」，避免把预告态误写成正式报名态。
